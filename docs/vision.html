The problem

Integration that couples to what changes fastest

  • Micro-frontends & per-team UIs — every solution ships its own code, CSS, and shell. Branding drifts, and every screen change is a hub deploy.
  • "AI / MCP / API" as three programs — each treated as a separate integration effort, multiplied by the number of solutions.
  • The real risk isn't old tech — it's coupling to things (models, MCP wire, UI frameworks) that churn every 6–18 months.

The question: what does the architecture bet on, and how fast does each bet decay?

Scale

Add the 20th satellite — the hub doesn't grow

  • The hub is one codebase — one renderer, shell, brand, and auth. It does not grow when satellites do.
  • Onboarding = one registry line plus the team's own declaration. Zero hub UI work per satellite.
  • UI upkeep is O(1) in N — fix the renderer once and every screen across every satellite benefits.
  • 3 today, 30 tomorrow — same hub, same team, same maintenance lift.
05 / 15

The durability thesis

The declaration is the asset

  • It can't rot separately from the product — it is the product's UI. A team that stops maintaining its declaration has stopped shipping UI. Self-enforcing.
  • Capability declarations: 10+ year half-life — a domain artifact, not a tech one. Everything else renders it.
  • Tenancy / authorization / audit — permanent by design; treated as unchangeable.
  • Every fast-decaying dependency sits behind a platform-owned seam. No satellite ever imports one.

A 2029 rewrite of the hub costs weeks, not a program — because the declarations don't move.

The part you cannot refactor later

Tenancy · authorization · audit

  • Authorization isn't hub-dependent — each satellite enforces its own tenant scoping. Call it directly with the wrong tenant's token and it refuses.
  • Audience default-deny — an unmarked screen is invisible to external principals and absent from the public API. You never add "external" to make something work.
  • Writes are invisible until named — a mutation reaches a model only when a human names it in the governance file; irreversible ones stay agent-invisible entirely.
  • Regulated-data audit, by construction — from the log alone: which records the agent read, for whom, when.
11 / 15

Identity & access

Keycloak login, satellite-declared roles

  • Satellites declare, the hub decides — a screen names the roles that may see it; the hub enforces at one chokepoint; each satellite re-checks.
  • Any-of & opt-in — hold one of the named roles; a screen that names none isn't role-gated. Internal only — partners are governed by audience + the public API.
  • Keycloak is the source of truth — org roles ride the login token into the Principal; the platform registry can narrow, never widen.
  • The matrix — finance → orders · engineering → orders + fleet · platform → fleet + depots · leadership → everything.
